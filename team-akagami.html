Abstract

Adamantium Gaming Hub is a college project that presents a War Thunder Mobile themed community gaming hub. It brings together a landing page, sign-in page, and three mode pages for ground vehicles, aircraft, and naval vessels. The mode pages combine vehicle catalogs and tactical guides with community rooms, join-request workflows, and room scoreboards. The front end is built with HTML, CSS, and JavaScript; Supabase provides hosted authentication and a PostgreSQL database accessed through the Supabase JavaScript client. Row Level Security (RLS) policies control database operations. This report describes the requirements, architecture, data model, implementation, testing plan, schedule, risks, results, limitations, and possible extensions.

1. Introduction

1.1 Project overview

Adamantium Gaming Hub is an independent fan-made web project created for a college assignment. It provides a single place to browse War Thunder Mobile themed ground, air, and naval content. The interface uses a dark visual theme with warm, muted champagne gold layout, image showcases, navigation between mode pages, and Supabase-backed community functions.

1.2 Objectives

Present ground vehicles, aircraft, and naval vessels in separate browsable catalogs.

Provide a shared sign-in flow for users who want to create rooms or participate in room workflows.

Allow signed-in users to create and manage their own rooms and submit join requests to other eligible rooms.

Show room scoreboards and mode-specific tactical guides.

Keep access controlled through Supabase authentication and database RLS policies.

1.3 Scope

The project covers a static browser-based front end and a hosted Supabase backend. It includes the home page, login page, and ground, aviation, and naval pages. It does not implement live gameplay, matchmaking with War Thunder servers, payments, native mobile applications, or an official relationship with the game publisher. Showcase media is stored as local project assets or referenced by the page; it is separate from catalog records.

2. Software Requirements Specification (SRS)

2.1 User classes

User classTypical capabilities
VisitorBrowse public catalog, guides, open rooms, and public scoreboards; sign in to use account features.
Signed-in playerCreate a room, request to join another room, view own request state, and use account controls.
Room ownerManage own room and review/respond to join requests, subject to the mode page and database policies.
Project maintainerManage catalog, guide, demo, and security data through the Supabase project.

2.2 Functional requirements

The system shall provide navigation among Home, Tanks, Aviation, Naval, Rooms, Guides, and Login destinations where present.

The system shall authenticate users through Supabase Auth and reflect the signed-in state in the interface.

The system shall read vehicle, aircraft, vessel, and guide records from the database.

The system shall list rooms by mode and allow an authenticated user to create a room.

The system shall allow a user to request access to an eligible room and display the request status.

The system shall allow room owners to respond to requests and manage rooms they own.

The system shall display scores associated with a selected room and support refreshing the list.

The system shall display clear loading, empty, and error states when data is unavailable.

2.3 Non-functional requirements

Usability: consistent navigation, readable contrast, responsive layouts, and clear status feedback.

Security: database access is protected by Supabase Auth and RLS; browser code must not contain service-role secrets.

Reliability: data-loading failures should be reported without fabricating database records.

Maintainability: mode pages and SQL scripts should remain organized and documented.

Compatibility: pages should work in a modern browser with JavaScript enabled and network access to Supabase.

Performance: keep local media reasonably sized and avoid unnecessary repeated database requests.

3. System Analysis and Design

3.1 Architecture

The browser loads static HTML, CSS, JavaScript, and media files. The Supabase JavaScript client communicates directly with the hosted Supabase API. Supabase Auth manages account sessions; the Data API applies PostgreSQL permissions and RLS policies before reading or changing public-schema rows. The current local workflow uses a development server. GitHub stores the project source; publishing the static site requires a hosting configuration and a deployed URL.

3.2 Data model and ER diagram

The current inventory discussed during database cleanup contains fourteen application tables: profiles, guides, three catalog tables, and three tables for each of the three room modes. Authentication identities are maintained by Supabase Auth in auth.users. Foreign keys connect room ownership and player/request identities to Auth users, while request and score rows reference their corresponding mode room. Some demo scoreboard entries are display-only and use a nullable player identity.

5.3 Database and security design

The current table inventory consists of profiles, guides, vehicles, aircraft, naval_vessels, and the room/request/score triplets for tanks, aviation, and naval. Saved SQL scripts are grouped under supabase/queries (including mode setup, guides, demo data, and security). The security script enables RLS and defines policies for public catalog/guide reads, room operations, request visibility and owner decisions, and score access as configured for each mode. The browser uses a publishable key; it is not a secret. A service-role key must never be placed in client-side HTML or JavaScript.

Repository note: the SQL currently lives as saved query scripts, while the project does not yet contain a confirmed ordered migration history pulled from the hosted database. Therefore, the scripts are useful project records but a clean, automated database rebuild has not been established by the repository alone.

8. Conclusion

Adamantium combines a multi-page War Thunder Mobile themed interface with Supabase-backed catalogs, guides, authentication, rooms, join requests, and scoreboards. The project demonstrates front-end development, relational data modeling, hosted authentication, and row-level access control. The main remaining report and release tasks are to record formal test outcomes, confirm the deployed hosting setup, verify all assets on the hosted site, and maintain a reproducible ordered database migration history. Potential future enhancements include a moderator/admin interface, stronger input validation and accessibility review, pagination/search for catalogs, and a documented automated deployment workflow.
